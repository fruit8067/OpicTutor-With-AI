## 0. 목표와 범위

**로그인 없이 모의 OPIc을 완주하고, 전체 답변에 대한 AI 예상 등급과 개선 피드백을 받는다.**

- 한국어 UI의 데스크톱 웹, 영어 문항·TTS·답변, 로컬 실행 MVP.
- 실제 인증 없음. 더미 로그인 UI는 실제 비밀번호를 받지 않는다. `session_id`는 시험 식별자이며 인증 수단이 아니다.
- 기본 8문항. 문항 수·재생 횟수·녹음 제한은 앱의 모의고사 규칙이다.
- **TTS 재생과 간단한 캐릭터 애니메이션은 필수다.**
- 한 문항 연습 모드, 후속 채팅, 재연습 비교, 페르소나, 실제 회원 관리, 외부 배포는 후속 범위다.
- 예상 등급은 참고용이며 공식 시험 성적이나 검증된 합격 보장이 아니다.

## 1. 흐름의 핵심 규칙

1. 설정 완료 후 전체 문제 세트와 순서를 한 번만 확정하고 DB에 보관한다.
2. 선택된 모든 문항의 TTS 준비가 끝나야 시험을 시작할 수 있다.
3. 시험 중 다음 문항 요청은 확정된 목록 조회다. 재추첨·실시간 LLM 출제를 하지 않는다.
4. 문항 음성은 웹에서 캐릭터와 함께 재생한다. 사용자에게 음성 다운로드를 요구하지 않는다.
5. 마이크 버튼 한 번으로 녹음 시작, 다시 누르면 종료·업로드한다.
6. 원음 저장 → STT → 문항에 연결된 답변 저장이 완료된 뒤 다음 문항으로 진행한다.
7. 마지막 예정 문항까지 답변 저장이 완료되어야 시험을 종료한다.
8. 등급 평가·피드백 LLM은 종료 후 전체 답변을 대상으로 호출한다. 시험 중에는 평가를 시작하지 않는다.
9. 서버가 DB에서 필요한 데이터·평가 기준을 조회해 AI에 전달한다.
10. AI가 예상 등급·피드백을 생성하고 서버가 검증·저장한 결과를 보여 준다.

## 2. 등급과 결과의 의미

출력 범위는 `NL < NM < NH < IL < IM1 < IM2 < IM3 < IH < AL`이다. 이번 MVP는 이 범위 밖의 등급을 출력하지 않는다.

| 화면 티어 | 예상 등급 |
| --- | --- |
| Bronze | NL, NM, NH |
| Silver | IL, IM1 |
| Gold | IM2, IM3 |
| Platinum | IH |
| Diamond | AL |

- AI가 전체 응답을 고려해 예상 등급과 근거를 생성한다. 서버는 등급을 티어로 매핑한다.
- 기존 0.6:0.4 가중치·후반부 1.5배·길이에 따른 자동 강등은 이번 등급 산출 규칙에서 제외한다.
- 근거 없는 정밀한 등급 거리를 표시하지 않고 다음 학습 목표를 문장으로 제시한다.
- 판단 근거가 부족하면 `insufficient_evidence`와 사유를 반환하고 등급을 비운다.
- 전체 답변을 전반적으로 평가하는 방향으로 설계하되 공식 채점 시스템을 재현했다고 주장하지 않는다. [OPIc 공식 시험소개](https://www.opic.co.kr/opics/servlet/controller.opic.site.about.AboutServlet?p_process=move-introduce-opic)

## 4. 기능 상세

### F0. 설정과 사전 준비

입력은 마이크 테스트 완료와 선택적 `scenario_id`다. 선택하지 않으면 기본 구성을 적용한다. 테스트 음성은 저장하지 않는다.

서버는 다음 순서로 처리한다.

1. 지원 시나리오인지, 출제 가능한 문항이 충분한지 검증한다.
2. 시험 세션을 만들고 전체 8문항·순서를 확정한다.
3. `sessions.settings_json`과 `session_questions`에 설정, 문항 ID·텍스트·유형·버전, 순서를 저장한다.
4. OmniVoice로 사전 생성·반입한 TTS 캐시의 문항 텍스트 해시·음성 설정을 확인하고 전체 문항에 연결한다. 누락·오래된 음성이 있으면 준비 실패로 표시하고 운영자의 재생성·반입 후 같은 세트로 재시도한다.
5. 모든 문항 음성이 준비됐는지 확인하고 세션을 `ready`로 변경한다.
6. 준비 완료 화면에서 사용자가 시험을 시작하면 첫 문항을 재생한다.

**불변 조건:** 같은 세션에서 준비 재시도·새로고침을 해도 문항과 순서는 바뀌지 않는다. 설정 변경은 이전 준비 세션을 취소하고 새 세션을 만든다. 이전 작업의 늦은 완료가 취소된 세션을 다시 활성화하지 못하게 한다.

**시나리오 정책:** 실제 지원 가능한 시나리오만 노출한다. 문항 부족 시 선택 해제·다른 설정 선택을 안내한다. 선택을 무시한 임의 대체는 하지 않는다. 공통 자기소개와 시나리오별 문항의 구성은 구분할 수 있다.

**출제 원천:** `rag_docs/build/questions.jsonl`의 검토된 pilot 문항을 사용한다. 현재 pilot 12개·todo 18개이며 Q000 자기소개는 추가 준비 대상이다. 불완전한 세트를 채우려고 같은 문항을 조용히 중복하거나 todo 자료를 그대로 사용하지 않는다.

| 순서 | 기본 구성안 |
| --- | --- |
| 1 | self_intro |
| 2 | description |
| 3 | routine |
| 4 | past_experience |
| 5 | comparison |
| 6 | roleplay_ask |
| 7 | roleplay_solve |
| 8 | issue 또는 roleplay_experience |

지원 시나리오 목록·문항 보강은 구현 전 확인 항목이다. 전체 세트 확정에는 LLM 호출이 필요 없다.

### F1. 모의고사와 문항 전환

1. 클라이언트가 현재 문항을 요청한다.
2. 서버는 상태·현재 순서를 확인하고 확정 문항과 TTS 재생 정보를 반환한다.
3. 웹에서 문항 음성과 캐릭터 애니메이션을 재생한다.
4. 재생 종료 후 마이크 버튼을 활성화한다. 다시 듣기는 문항당 1회라는 초기 앱 정책을 적용한다.
5. 같은 버튼으로 녹음을 시작·종료하고 오디오를 업로드한다.
6. “답변 처리 중”을 표시하며 **업로드 접수 후에도 현재 문항을 유지**한다.
7. `stt_status=done`과 DB 저장 완료 후 서버가 현재 순서를 전진시킨다.
8. 남은 문항이 있으면 같은 세트의 다음 문항을 요청한다. 마지막 답변까지 저장되면 종료한다.

`202 Accepted`는 업로드·작업 접수이며 STT 완료가 아니다. 미래 순서 문항 제출을 거절하고, 중복 요청으로 순서가 두 번 전진하지 않게 한다. 새로고침은 서버 상태로 복구한다.

### F2. 음성·STT·지표

- MediaRecorder 지원 형식을 확인하고 서버가 실제 형식·크기·길이를 검증한다.
- 초기 녹음 정책은 최소 2초, 최대 2분이다. 무음·손상·의미 있는 발화 없음은 재녹음을 요청한다.
- 원음은 `data/audio/{session_id}/{answer_id}.webm` 등 실제 형식으로 저장한다.
- 로컬 faster-whisper `small.en`을 시작점으로 사용한다. 최종 크기는 속도·품질을 측정해 결정한다.
- STT 텍스트·단어 타임스탬프·지표를 문항에 연결한다. 시험 중 등급 평가 작업은 생성하지 않는다.

| 지표 | 정의 |
| --- | --- |
| duration_sec | 전체 녹음 길이 |
| speech_sec | VAD가 탐지한 발화 구간 길이 합 |
| word_count | 정의된 토큰화 규칙에 따른 영어 단어 수 |
| wpm | word_count / 전체 녹음 시간(분) |
| articulation_wpm | word_count / 발화 시간(분); 분모 0이면 결측 |
| long_pause_count | 발화 시작·끝 사이 1초 이상 비발화 구간 수 |
| observed_filler_per100 | STT에 남은 필러 수 / 기준 단어 수 × 100; 분모 0이면 결측 |

단어·필러 계산 규칙은 버전으로 관리한다. STT가 삭제한 필러가 복원된다고 가정하지 않으며, 관측 지표를 정확한 발음 평가로 표시하지 않는다. 기존 코퍼스 기준과 정의가 다르면 그대로 비교하지 않는다.

### F3. 시험 종료 후 종합 평가

**시작 조건:** 세션이 `submitted`이며 예정된 모든 문항의 채택 답변과 STT 저장이 완료되어야 한다. 종료 시 채택 답변 ID를 고정한다.

**주체:** 서버가 DB를 조회한다. LLM이 DB에 직접 접속하거나 SQL을 실행할 필요는 없다.

| 입력 | 조회 방법 |
| --- | --- |
| 전체 문항·순서·시나리오 | 세션 출제 스냅샷 |
| 전체 STT 답변·지표 | 고정된 채택 답변 ID |
| 등급별 루브릭 | 버전이 고정된 루브릭 |
| 대조 예시 | 동일 문항의 세트 직접 조회 우선; 없으면 같은 유형의 유사 문항 검색 |
| 개선 패턴 | 버전이 고정된 승급 패턴 자료 |

기본안은 **전체 시험 데이터와 선별 근거를 한 번의 구조화된 LLM 요청에 넣어 예상 등급·피드백을 함께 생성**하는 방식이다. 근거 자료의 토큰 예산을 제한하되 사용자 문항·답변은 임의로 누락하지 않는다. 한도를 넘으면 조용히 잘라내지 않고 오류로 기록한다. 계층적 요약 등 대체 방식은 검증 후 명세를 변경한다.

출력 계약:

```text
status: assessed | insufficient_evidence
estimated_level: NL ... AL 또는 null
headline: 한국어 총평
grade_rationale: 전체 시험에 근거한 판단 사유
dimension_scores: 과제 수행 / 문장 구성 / 정확성 / 관측 유창성 (내부 1~5)
items[]: order_no, evidence[], mistakes[{quote, problem, fix}], upgrade_tip
feedback_cards[3..5]: title, why, before, after, related_order_nos
limitations[]: 음질·STT·근거 부족 등 한계
```

- Pydantic으로 형식·점수·등급 범위·문항 참조를 검증하고 인용문이 실제 답변에 있는지 확인한다.
- 판단 불충분이면 등급을 비우고 가능한 관측·피드백과 사유만 표시한다. 이때 카드 수는 줄어들 수 있다.
- 등급은 AI 생성 값을 검증해 저장한다. 서버가 고정 가중 평균으로 다시 산출하지 않는다.
- 사용자 답변·검색 문서는 지시가 아닌 평가 데이터다. AI에 DB 쓰기 권한을 주지 않는다.
- 모델·프롬프트·루브릭·코퍼스 버전과 참조 자료 ID를 저장한다.
- 일시적 API 오류는 최대 2회 추가 재시도한다. 거절·중단·입력 오류를 성공 처리하지 않는다.
- 실패하면 전체 답변을 보존하고 평가만 다시 실행한다. 문항을 임의로 빼고 다른 구성의 시험 등급을 만들지 않는다.

기본 8문항 시험의 호출은 **로컬 STT 8회 + 종료 후 외부 평가·피드백 LLM 1회**다. 운영자의 사전 TTS 생성, 근거 임베딩, 오류 재시도, 검증 호출은 별도다. 세션 준비에서는 TTS 모델을 호출하지 않는다. 실제 비용·정확도는 측정 전 미확정이다.

### F4. 결과 화면

- 예상 등급·티어, 전체 근거, 영역별 진단, 개선 카드 3~5장, 문항별 상세를 표시한다.
- `before`는 실제 답변, `after`는 수정 예시다. 사용자 경험을 새로 추가하면 연습용 예시라고 구분한다.
- 등급이 없으면 낮은 등급으로 대체하지 않고 평가 불가 사유를 보여 준다.
- DB 저장 후 결과를 제공한다. 새로고침·재조회는 AI를 다시 호출하지 않는다.
- 재평가는 새 실행 버전으로 저장하고 세션의 현재 결과를 연결한다.

### F5. 검증

- 합성 데이터 형식 검사와 실제 채점 정확도 검증을 구분한다. 기존 216개 문서는 12문항 × 9등급 × clean/stt 변형이다.
- 코퍼스 평가에서는 동일 대조 세트의 모든 등급·변형을 직접 조회와 유사 검색 양쪽에서 제외한다.
- 종합 등급 검증에는 전체 답변 세트와 대응 평가가 필요하다. 단일 문항 합성 평가만으로 종합 정확도를 주장하지 않는다.
- 정확 일치율, ±1등급 일치율, 평균 등급 오차, 혼동 행렬, 반복 평가 변동을 기록한다. ±1등급 80%는 목표다.
- 세트 불변성, 시나리오 반영, TTS 실패, 업로드 중복, STT 완료 전 이동 차단, 조기 종료 차단, 시험 중 평가 미호출, 중복 종료를 확인한다.

### F6. TTS — OmniVoice 사전 생성과 세션 준비

- 원격 변경을 반영해 Azure TTS 대신 **OmniVoice + Google Colab 사전 생성**을 사용한다. 제공된 [노트북](../colab/omnivoice_tts.ipynb)을 보존한다.
- 운영자가 문항·진행자 대사 음성을 미리 생성해 로컬 서버에 반입한다. 사용자 설정 단계에서 Colab이나 실시간 TTS API를 호출하지 않는다.
- 사전 생성된 음성과 별개로, 설정 단계에서는 **해당 세션 전체 문항에 정확히 대응하는 음성의 존재·버전을 확인하고 연결**해야 ready가 된다.

사전 준비 과정(노트북은 존재하며 export 스크립트는 구현 대상):

```text
운영자: export_tts_jobs로 jobs.jsonl 생성
→ Colab의 omnivoice_tts.ipynb에 문항·진행자 대사만 전달
→ Voice Design으로 만든 기준 음성으로 문항 음색 통일
→ mp3·manifest.json을 tts_mp3.zip으로 내려받기
→ backend/static/tts/에 반입
→ 사용자 설정 시 서버가 선택 문항의 음성·해시 검사 및 연결
```

- 실제 수험생 음성을 Colab에 보내지 않는다. 기준 음성은 새로 생성한 합성 음성을 사용한다.
- 노트북의 manifest에는 항목별 ID·text_sha1·길이와 엔진·instruct·seed·speed·num_step 설정이 들어간다. 기준 음성·모델의 정확한 버전까지 추가 관리하는 것은 구현 대상이다. 현재 노트북이 모든 버전 검사를 이미 제공한다고 가정하지 않는다.
- 문항이나 음성 설정이 바뀌면 운영자가 해당 음성을 재생성·반입한다. `export_tts_jobs --stale`은 변경·누락 문항을 내보내도록 구현한다.
- 누락·해시 불일치 시 `prepare_failed`로 표시한다. 파일 준비 없이 자동 반복하거나 다른 문항으로 바꾸지 않는다. 원인이 해결된 후 사용자가 같은 세트로 재시도한다.
- 서버는 로컬 재생 URL/음성 응답을 제공하고 웹은 HTML audio로 재생한다. 내부 mp3 캐싱은 허용하되 사용자에게 파일 다운로드를 요구하지 않는다.
- 브라우저 재생 차단은 사용자 재생 동작으로 해소한다. 실패하면 현재 문항에서 재시도한다.
- 원격 초안의 Web Speech 자동 대체·텍스트만으로 진행은 이번 사용자 확인 흐름과 달라 채택하지 않는다. TTS·기본 캐릭터는 필수다.
- Colab 실행 환경·할당량은 별도 확인 대상이며 계정·GPU·사용량에 아무 제약이 없다고 보장하지 않는다.

### F7. 캐릭터

- 오리지널 SVG/CSS 캐릭터로 충분하다. 정교한 립싱크·영상 아바타는 요구하지 않는다.
- idle(대기), speaking(TTS 재생), listening(녹음), processing(업로드·STT)을 구분한다.
- 기본 애니메이션은 재생 시작·종료 이벤트에 연결한다. Web Audio 음량 반응은 보강 가능하다.
- 음성이 끝나면 speaking을 멈추고 녹음 버튼을 활성화한다. 재생과 녹음을 동시에 허용하지 않는다.

## 5. 상태와 사용자 흐름

```text
설정 제출
→ preparing: 전체 세트 확정·저장 + 전체 TTS 준비
→ ready: 시험 시작 가능
→ in_progress: 문항 재생 → 녹음 → 업로드 → STT 저장 → 다음 문항 반복
→ submitted: 마지막 답변 저장 확인·채택 답변 고정
→ grading: DB 전체 조회 → 근거 조회 → AI 평가·피드백
→ done: 검증한 결과 저장·표시
```

- 준비 실패: `prepare_failed` → 같은 세트 준비 재시도 → `preparing`.
- 준비 취소: `preparing/ready/prepare_failed` → `cancelled`; 새 설정은 새 세션.
- 답변 실패: 세션은 `in_progress`; 답변의 STT 실패·재녹음 필요 상태를 기록한다. 성공 전 순서를 전진시키지 않는다.
- 평가 실패: `grading` → `grading_failed` → 저장된 전체 답변으로 재시도.
- 판단 불충분은 정상 처리 결과의 `assessment_status=insufficient_evidence`이며 기술적 실패와 다르다.
- 조회 오류·음성 실패·통신 끊김은 남은 문항 없음이 아니다.

그림은 [FLOWCHART.md](FLOWCHART.md)를 함께 읽는다.

## 7. DB·파일·작업 설계

아래는 핵심 개념 모델이며 실행 DDL이 아니다. 주요 데이터에 생성·갱신 시각을 둔다.

| 테이블 | 핵심 필드 | 쓰는 시점 |
| --- | --- | --- |
| sessions | id, settings_json, scenario_id, status, question_count, current_order_no, selected_answer_ids, result_id, started_at, submitted_at | 설정 제출·상태 전이 |
| session_questions | id, session_id, order_no, question_id, question_version, question_text, question_type, tts_asset_id | 전체 세트 확정 |
| tts_assets | id, cache_key, text_hash, voice_id, settings_version, status, file_path, duration_sec, error_code | TTS 준비 |
| answers | id, session_question_id, attempt_no, client_request_id, audio_path, audio_hash, stt_status, stt_text, timestamps_json, metrics_json, stt_version, error_code | 업로드·STT |
| evaluations | id, session_id, run_no, selected_answer_ids, status, assessment_status, estimated_level, result_json, model, prompt_version, rubric_version, corpus_version, retrieved_doc_ids | 종료 후 평가 |
| rag_docs | id, doc_type, question_id, question_type, level, contrast_set_id, text_style, text, metadata, corpus_version, embedding | 코퍼스 적재 |
| jobs | id, type, target_id, dedupe_key, status, attempts, locked_until, next_run_at, error_code | 작업 등록·실행 |
| ai_requests | id, job_id, purpose, model, input_tokens, output_tokens, latency_ms, status, error_code | 외부 호출 메타 기록 |

- 문제 은행 원본은 JSONL에서 읽어도 **세션의 확정 문제 세트는 DB에 저장**한다. 원본 변경이 진행 중 시험에 영향을 주면 안 된다.
- `session_questions(session_id, order_no)`, `tts_assets.cache_key`, `answers.client_request_id`, `jobs.dedupe_key`에 중복 방지 제약을 둔다.
- 업로드 재전송은 같은 답변을 반환한다. 재녹음은 새 시도로 저장하고 STT 성공 시 채택한다.
- STT 성공과 현재 순서 갱신을 DB 트랜잭션으로 수행한다. 종료 시 전체 채택 답변을 고정하고 평가 작업을 중복 등록하지 않는다.
- API는 긴 작업 접수를 반환한다. 워커가 처리하고 클라이언트는 준비·답변·결과 상태를 각각 조회한다.
- 워커는 작업을 잠금으로 확보하고 유효 시간을 갱신하며, 비정상 종료 후 만료 작업을 복구한다.
- **STT 연산은 API 프로세스와 분리하되 사용자 흐름은 저장 완료를 기다린다.**
- 파일과 DB는 단일 원자적 저장이 아니므로 임시·고아 파일 정리와 작업 상태 복구를 마련한다.
- 중복 요청·늦은 작업 완료가 새 결과를 덮어쓰지 않도록 실행 ID와 상태를 확인한다.
- 상태 조회는 2초 간격으로 시작하고 완료·최종 실패·화면 이탈 시 멈춘다. 조회 자체는 AI 호출이 아니다.

## 8. 기존 API 명세 충돌 — 동기화 필요

`API_SPEC.md`는 이번 세 문서 수정 범위에 포함되지 않았다. 아래는 이전 흐름이므로 구현 시 그대로 적용하지 않는다. 구체적인 경로·HTTP 스키마는 API 개정에서 확정한다.

| 상태·재평가 | 준비·제출·단계별 실패 상태, 전체 답변 재사용 평가 |

## 10. 데이터 취급

- 로컬 API·DB는 로컬 인터페이스에 바인딩하고 허용 Origin을 제한한다.
- 키는 백엔드 환경 설정에만 두고 Git·프론트엔드·일반 로그에 노출하지 않는다.
- 수험생 원음과 STT는 로컬에서 처리한다. Colab에는 사전 음성 생성용 문항·진행자 대사만 전달하며, 평가 제공자에는 필요한 답변 텍스트·지표·근거를 전송한다.
- 텍스트에도 개인정보가 있을 수 있음을 안내하고 불필요한 식별정보를 최소화한다.
- `data/`와 키 파일은 Git에서 제외하고 답변 원문을 일반 운영 로그에 남기지 않는다.
- 자료의 출처·허용 사용 범위를 확인한다. 인증 없는 로컬 MVP를 그대로 공개 배포하지 않는다.
- 원음 보관·삭제 기간은 미정이다.
